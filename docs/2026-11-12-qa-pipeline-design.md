# 0-1 功能开发出题与评测流水线 设计文档

## 1. 目标

批量生产「CC/Codex 用户反馈标注」作业数据：AI 批量出 0-1 功能开发题，在全新会话中做题，AI 验收并写 Feedback 与录屏步骤，查验后录屏，最终在页面按提交表列顺序展示，逐格复制到提交表。

两种推进方式并存：手动模式下每个环节由人点按钮、人工做题与录屏；全自动模式下「补充题目池」不停出题，「开始做题」从题目池按顺序取题，自动完成准备环境、做题、收集、验收、查验与录屏，只在出错时停下等人处理（见 5.11）。

不在范围内：自动上传对象存储。

## 2. 总体架构

- **两套执行环境**：
  - 流水线 AI 环节（出题、验收、写 Feedback、写录屏步骤）使用 Windows 上的 Codex CLI，沿用本机当前的认证：默认为 ChatGPT 官方登录；用 CC Switch 等配置第三方供应商的环境，沿用 `config.toml` 中的供应商与模型。
  - 做题使用 WSL（Ubuntu-24.04）中的 Claude Code（已接入作业模型），保持干净环境。手动模式由人在终端里启动；自动做题时后端在独立的 tmux 服务器中启动同样的交互式会话并粘贴 prompt 原文，轨迹与人工做题一致；流水线不修改 `~/.claude` 的配置，也不用它做出题、验收等其他环节。
- **AI 工作由 skill 完成**：出题、验收、返修、生成自动录屏脚本封装成 Codex skill（`qa-gen`、`qa-review`、`qa-rework`、`qa-record`），放在 Codex 工作区的 `.agents/skills/` 下。
- **网页只做管理**：题目队列、状态流转、人工查验与改稿、配置、提交表展示；已完成题目可写入飞书多维表格（见 5.9）。
- **触发方式**：网页按钮触发，WSL 中的后端通过 WSL 互操作在后台启动 Windows 版 codex：

  ```
  <codex.exe> exec --json --ephemeral --ignore-user-config --skip-git-repo-check \
    -m <模型> -c model_reasoning_effort="<推理强度>" \
    -s danger-full-access \
    -C <Codex 工作区> \
    --output-schema <工作区>\schemas\<skill>.json -o <工作区>\runs\<运行ID>\result.json \
    '$<skill>'  < 输入文本
  ```

  - `--json` 的事件流逐行推送到页面，并保存到 `data/logs/`。
  - `--ephemeral` 不保存会话文件，流水线会话不出现在 Codex 客户端历史中。
  - `--ignore-user-config` 不加载 `~/.codex/config.toml` 中的 MCP、插件与默认模型，登录凭据照常使用。
  - 配置页勾选「沿用 config.toml 的供应商与模型」时，`-m <模型>` 换成 `config.toml` 的 `model`，并把 `model_provider` 与对应的 `[model_providers.<名称>]` 一节逐项转成 `-c` 参数（嵌套表展开为带点的键）；其余配置仍不加载。启动日志中键名像密钥的值打码。
- **输入与输出**：后端把本次所需数据拼成文本经 stdin 传入，开头给出本次运行 ID 与运行目录 `runs/<运行ID>/`（skill 的草稿与验证脚本只能放在这里）；skill 的最终回复受 `--output-schema` 约束为 JSON，后端校验后写入数据库。skill 不直接访问数据库。
- **模型**：配置页填写模型名与推理强度，默认 `gpt-6.1-sol` / `xhigh`；沿用 `config.toml` 时模型取其中的 `model`（没有时仍用配置页的模型名），推理强度始终用配置页的值。
- **登录保护**：只使用 Windows 默认的 `~/.codex`，与 Codex 客户端共用同一份 `auth.json`（ChatGPT 登录或 CC Switch 写入的第三方 key）；流水线只读 `config.toml`，不读、不改 `auth.json`；不得复制 `auth.json`，不得在 WSL 中运行 Linux 版 codex 并指向 Windows 的 `.codex` 目录。
- **共享数据**：`data/pipeline.db`（SQLite）只由后端读写；表结构由 `app/sql/` 下的初始化与增量脚本维护，基础审计列按统一规范（SQLite 不支持 `comment on`，字段说明以行内注释给出）。
- **后端服务**：FastAPI 运行在 WSL，只监听 `127.0.0.1`，默认端口 8765，在 Windows 浏览器中通过 `http://localhost:8765` 访问。
- **GitHub 凭据**：推送使用 WSL 中已配置的 ssh 凭据，配置页只填写仓库 ssh 地址。
- **技术栈**：Python 3.12、FastAPI、SQLite、原生 HTML/JS、openpyxl。

## 4. 题目状态流转

```
待初始化 → 待准备环境 → 待做题 → 待收集 → 待验收 → 待查验 → 待录屏 → 已完成
                          ↑         │                 ↑        │
                          └─ 重做 ──┘                 └─ 打回 ─┘（附意见重新生成）
任一自动环节失败 → 失败（保留日志，可重试）

已完成 ──粘贴待返修质检──→ 待返修（AI 处理）──┬─ 产物未变且无需重录 → 已完成
                                              └─ 产物有改动或需重录 → 待录屏 → 已完成
（质检不通过的数据直接放弃，不进流水线）
```

全自动模式沿用同一套状态：调度器按状态启动对应环节（待查验由规则自动判断、待做题与待录屏由后端驱动），出错时题目停下并记录停下信息，不新增状态（见 5.11）。

## 5. 各环节说明

### 5.1 批量出题（skill `qa-gen`）

- 甲方序号：出题前在表单里填一批可用的甲方序号（逗号、顿号或空白分隔，连续的可写成 `12100-12107`，一次 1 到 10 个），题目数量即序号个数；序号不能重复，也不能是库内未删除题目已占用的。入库的题按顺序分配这批序号，出题期间被别的题占用的不再分配，没用上的序号写在运行日志里。
- 输入（页面填写，后端经 stdin 传入）：数量（取甲方序号个数）、所属领域与子方向（所属领域固定为「游戏、图形与多媒体」，子方向取音视频处理、图形渲染、游戏开发、图像处理、其他）、难度（仅困难/地狱）、技术栈偏好（可选），以及库内已有题目摘要（用于查重）。
- 出题约束（写入 skill 与 `banned-topics.md`）：
  - 必须是 0-1 功能开发，任务类型固定为「功能开发」；
  - 必须能在 WSL Ubuntu-24.04 中构建与运行：命令行与服务端直接运行；图形界面通过 WSLg 显示；网页由 WSL 启动服务、在 Windows 浏览器访问 `localhost`；依赖显卡能力（WebGPU、OpenGL 4.5 等）的题须在输出中标明，初始化时按 5.3 确认可用；
  - 禁止使用 docker；
  - 避开作业文档中的雷同题清单，且不得满足「过于简单」的判定特征；
  - 依赖的外部站点或接口须列出地址，初始化时逐一测通，测不通的从题目中去掉。
- 输出（`schemas/qa-gen.json`，每题）：
  - 分支名（项目短名，小写加连字符，如 `live-relay`，库内唯一）；
  - User Prompt（用户口吻）；所属领域、子方向、任务类型、任务难度、语言/框架；
  - 内部验收要点（只用于验收环节，不出现在 prompt 中）；
  - 所需素材清单：文件路径、用途、获取方式（下载地址或生成脚本）、许可说明、预计大小；
  - 环境需求：工具链及最低版本、是否依赖显卡、外部站点地址；
  - 备注草稿：素材说明与环境前置条件（如「需先安装 FFmpeg samples 预置 1080p 测试视频」）。
- 与库内已有题目查重，避免雷同。
- 后端校验输出后入库：schema 把子方向限定为领域表中的取值，入库时再校验子方向属于所选领域，不合规的题目跳过并记录日志；页面修改领域或子方向时同样校验。生成后可在页面编辑或删除，任务难度以人工确认结果为准。

### 5.2 初始化（后端脚本，不调用 AI）

- 人工核对题目后点一次「初始化并准备环境」，后端在一次运行中依次完成初始化（本节）与准备环境（5.3），全部通过直接进入「待做题」，只在需要人工处理时停在「待准备环境」。
- 在统一的 GitHub 仓库（须对评测团队可访问）中为每题创建孤儿分支 `<分支名>`，加入 `.gitignore`：只忽略凭据文件（`.env`、`*.key`、`*.pem` 等）和缓存目录，不使用宽泛的产物类型规则。
- 检出到 `~/jianzhi/feedback-tasks/<分支名>/`，此时不推送，进入「待准备环境」并紧接着准备环境。
- 初始化中途失败（如查询远端分支时网络出错）时，做题目录里只留下空仓库（只有 `.git` 与 `.gitignore`、没有任何提交），重试时清掉后重新初始化；目录里有其他文件或已有提交时拒绝初始化。

### 5.3 准备环境（后端脚本，只在异常时需要人工）

- 执行顺序：工具链检查（素材生成脚本可能依赖这些工具）→ 素材 → 显卡 → 外网 → 做题客户端体检 → 没有待处理项时提交初始快照。
- 素材：下载类自动下载，脚本类自动在做题目录执行生成脚本，已就绪的只核对不重跑（文件丢失时按来源重新获取）；只能人工准备的素材检查是否已放到对应路径。单文件不得超过 100MB（GitHub 上限），超过 50MB 时页面提示。
- 需要人工处理的情况：人工素材未放入、下载或脚本失败、素材超过 100MB、工具链缺失或版本不够、外网不通、做题客户端不干净、依赖显卡需人工确认（关闭「自动确认显卡能力」时）。题目停在「待准备环境」，详情顶部逐项列出问题和处理方式；处理完点「继续准备」重新跑一遍检查，依赖显卡的题点「确认显卡能力并继续」。
- 自动确认显卡能力（配置项，默认开启）：依赖显卡的题准备时直接把显卡能力记为通过，不再停下等人工确认；环境检查明细里保留读到的 OpenGL 信息并注明「已按配置自动确认」。
- 题目环境检查（在 WSL 中执行）：
  - 工具链：在做题目录逐项检查环境需求中的系统级工具命令与版本，缺失时页面给出安装命令；项目依赖（检查命令指向 `.venv`、`node_modules` 或相对路径）不预检也不预装，做题时由模型自己安装；
  - 显卡能力：依赖显卡的题检查 WSLg 下的 OpenGL 版本，或在 Windows 浏览器中确认 WebGPU 可用，不满足时退回修改题目；
  - 外网连通性：逐一请求外部站点地址，记录状态码与耗时；
  - 结果按题保存，在题目详情的「环境检查」卡片中展示。
- 做题客户端体检（检查 WSL 的 `~/.claude`）：
  - 不存在全局 CLAUDE.md、rules、用户 skills、MCP 服务器、已启用插件；
  - `settings.json` 的 `env` 中 `CLAUDE_CODE_MAX_CONTEXT_TOKENS` 为 `1000000`、`DISABLE_COMPACT` 为 `1`、`ANTHROPIC_BETAS` 包含 `context-1m-2025-08-07`；
  - 推理强度：`settings.json` 中若设置了 `effortLevel` 必须为 `high`；未设置时以收集环节的轨迹校验为准（轨迹每条模型回复都记录 `effort`）；
  - 记录当前 `ANTHROPIC_MODEL`，供收集时比对。
- 全部通过后自动提交并推送，记录初始快照（40 位 SHA permalink），进入「待做题」；任一项不通过时不提交，页面标红列出。运行中途出错（如推送失败）时题目置为「失败」，重试会重新执行整个准备。
- 页面提供一键复制的做题命令（`cd ~/jianzhi/feedback-tasks/<分支名> && claude --dangerously-skip-permissions`，以 bypass 模式启动）和 prompt 原文。

### 5.4 做题（人工）

- 在 WSL 的做题目录以 bypass 模式启动全新 Claude Code 会话，使用 auto 模型发送一次 prompt，模型回答结束即完成，不追问、不纠错。
- 模型无报错中途停止、或出现网络/接口报错时，点击「重做」：
  - 当前会话的 SessionID 记为作废；
  - 做题目录执行 `git reset --hard <初始快照>` 与 `git clean -xfd`，恢复到初始状态；
  - 回到「待做题」，重新开新会话发送 prompt。
- 只有在多次重做仍无故中断（模型无报错停止）时，才允许在同一会话中输入「继续」，此时 prompt 与 TurnID/PromptID 取第一轮，评价基于「继续」后的最终结果。
- 接口报错中断（如 504、529）不能输入「继续」，必须重做：Claude Code 会把报错写成一条 `message.model` 为 `<synthetic>` 的助手消息留在轨迹里，甲方质检按模型不符判不通过。自动做题按配置自动作废重做（见 5.11）。
- 页面记录做题完成时间：当天 20:00 前完成的题，列表中标记「今日必须提交」。

### 5.5 收集（后端脚本，不调用 AI）

- 在 WSL 的 `~/.claude/projects/<做题目录编码>/` 下定位本题轨迹 jsonl：排除已作废的 SessionID，取最新一个首条用户输入与 prompt 原文一致的会话。
- 校验：
  - 用户输入只有 prompt 原文一条，或其后仅跟「继续」（此时自动在备注中写入「无报错停止」、继续次数与处理方式）；
  - 主链上没有 `message.model` 为 `<synthetic>` 或带 `isApiErrorMessage` 的助手消息（接口报错、会话被打断时客户端写入的占位消息），有则校验不通过，需要重做；
  - 无 MCP、子代理调用；Skill 调用只允许调用 Claude Code 内置 skill（如模型画图时自行加载 `dataviz`）；轨迹中的 skill 列表只包含 Claude Code 内置 skill；
  - 轨迹中的模型与 5.3 记录的 `ANTHROPIC_MODEL` 一致；
  - 每条模型回复的推理强度均为 `high`。
- 提取：SessionID、TurnID/PromptID（第一轮 user 消息的 `promptId`）、Harness（固定「Claude Code CLI」）、Harness 版本、模型、操作系统（固定「Linux」）、工作目录、做题完成时间。
- 补交被忽略文件时，凭据类文件（`.env`、`*.key`、`*.pem` 等）一律不补交；被忽略的目录先展开为文件再逐个过滤。
- 提交产物：
  - 先检查远端分支：若会话期间被推送过，校验初始快照仍是其祖先，且没有被强推改写；
  - `git add -A`；对比会话前后被忽略的文件，把会话期间新出现的被忽略文件用 `-f` 加入（排除 `node_modules`、`.venv`、`__pycache__`、`dist`、`build` 等依赖与缓存目录）；
  - 提交信息固定为 `feat: 模型产物 - <分支名>`，点「开始收集」直接执行，不再询问概述；
  - 推送后记录产物快照（模型自己提交过多次则以最后一次为准，不 squash），并校验初始快照是其祖先提交。
- 生成轨迹摘要：按时间顺序列出每次工具调用（工具名、参数要点、结果是否报错）、改动的文件、报错原文、模型最终回复；同时保存完整 jsonl 的 `\\wsl.localhost\...` 路径。
- 复制轨迹 jsonl 到待上传文件目录（配置项，默认 `E:\WorkSpace\jianzhi\feedback-upload`），文件名为「甲方序号-分支名.jsonl」（没有甲方序号时只用分支名），与自动录屏放在一起；重做后再收集时覆盖。修改甲方序号时，该目录里这道题的轨迹与录屏随之改名。

### 5.6 验收与写 Feedback（skill `qa-review`）

- 后端将产物快照全新克隆到 `~/jianzhi/feedback-verify/<分支名>/`，为本题分配一段端口，再启动 skill。
- 输入（经 stdin）：题目字段、内部验收要点、环境检查结果、轨迹摘要、完整轨迹路径、产物 diff、分配的端口段、打回时的人工意见。
- 执行方式：
  - 安装依赖、构建、测试、运行等命令统一通过 `wsl.exe -d Ubuntu-24.04 --cd /home/<用户>/jianzhi/feedback-verify/<分支名> -- bash -ic '<命令>'` 在 WSL 中执行（`-i` 用于加载 nvm 等交互式环境）；
  - 读取代码使用 `\\wsl.localhost\Ubuntu-24.04\home\<用户>\jianzhi\feedback-verify\<分支名>\` 路径，需要细节时按完整轨迹路径检索；
  - 单条命令设置超时；服务类进程在分配的端口上后台启动，验证完成后必须结束；
  - 界面与画面类验证使用 WSL 中预装的 playwright（chromium）截图（ffmpeg、playwright、mesa-utils 由 `scripts/setup-verify-tools.sh` 安装）；工具缺失时如实记录未能验证，不计入模型问题；音视频类使用 ffprobe、ffmpeg 检查编码、时长、码率、响度等参数；依赖显卡、无法在无头浏览器中验证的项，证据标记为「需录屏确认」。
- 权限边界（写入工作区 `AGENTS.md`）：只能写入 `verify/<分支名>` 与本次 `runs/<运行ID>`；不得修改做题目录、WSL 的 `~/.claude`、Windows 的 `~/.codex`；不得执行 `git push` 或改写 git 历史。
- 输出（`schemas/qa-review.json`）：
  - 证据清单：每条包含现象、执行命令、输出摘录、是否可在录屏中展示；
  - 交付完整性评分（1–5）及评分理由（引用证据）；
  - Feedback 文本（遵循 `style.md`，覆盖过程与产物，优先写在产物页面上用正常操作就能看到的问题）：一般 150 到 300 字，不超过 400 字；5 分写做好了什么，1 到 4 分只写没做好什么，只写一个最关键的过程问题和一到两个影响最大的产物问题，每个产物问题一个代码锚点，其余问题只留在证据清单；不套固定开头，直接从最关键的事实写起；
  - 录屏前准备（`record_prep`，不录）：`setup` 在录屏目录终端执行，安装依赖、生成需要的特殊输入文件、后台启动服务并打出访问地址；`cleanup` 录完后结束服务；
  - 录屏步骤（真正录制的部分）：1 到 3 步，60 秒左右，最长 90 秒；第一步直接打开产物页面操作出第一个问题，只录 Feedback 里写到的内容（每个产物问题各一步，失败项照录；5 分录核心功能跑通）；证据放在产物页面上的正常操作里（按钮、下拉框、输入框、导入文件），不在录屏中跑脚本、生成文件或注入控制台脚本，控制台脚本只在必须定位精确像素时使用；命令用相对路径，不加 `wsl.exe`、`bash -ic` 包装。输入中的「录屏环境」一节给出录屏目录（WSL 路径与 Windows 访问路径）与这些写法，页面录屏卡片对带包装、用了验收或做题目录路径、要求点精确像素、录制部分含启动结束服务、临时脚本或控制台注入的步骤标出提示；
  - 环境可复现等级，三选一：「无外部依赖」「有外部依赖，未容器化」「已容器化，可一键起环境」（随初始快照提交的素材不算外部依赖）；
  - 备注（在出题备注草稿基础上补充中断说明等）。
- 输入中附带素材清单与生成脚本，需要换参数重新生成素材时在验收目录内执行，不覆盖已提交的素材。
- 写作要求：
  - 只写模型自身能力造成的问题，不写环境、网络波动导致的问题；
  - 输出前自检评分与描述一致：描述中有核心需求未实现或无法运行时不得给 4–5 分，给 4–5 分时同样要列出逐项核对的需求点与运行结果。
- 单次运行设置总超时（默认 60 分钟，可配置）；超时、额度限流或认证失败时置为「失败」并显示原因。

### 5.7 查验（人工）

页面展示证据清单、轨迹摘要、评分与 Feedback；可直接编辑，或填写意见后重新生成；选择通过（进入待录屏）或打回。环境可复现等级必须从三档中选定才能通过。证据清单只用于核对 Feedback 的依据和挑选录屏内容，不进入提交表。

### 5.8 录屏（人工）

- 点击「准备录屏环境」：后端将产物快照全新克隆到 `~/jianzhi/feedback-record/<分支名>/`，保证从干净状态开始；页面「录屏」卡片给出进入该目录的命令，录屏前准备、录屏步骤与录完收尾的命令均在该目录下执行，每条命令右上角可一键复制。准备成功后记下就绪标记（准备时的产物快照与时间），详情顶部显示「录屏环境已就绪」，录屏卡片显示就绪时间与快照，按钮变为「重新准备录屏环境」（会先确认，因为要删掉录屏目录重新克隆）；返修推送了新的产物快照或录屏目录被删时视为未就绪。
- 先执行录屏前准备（不录），再按页面录屏步骤录制（720p、mp4、90 秒以内，从产物页面上的问题开始，失败与报错过程不剪），停止录制后执行录完收尾。
- 录屏文件：页面自动读取录屏目录（配置项，默认 `E:\GSB-Recordings`）中最新的 5 个 mp4，默认选中最新一个，并显示修改时间、大小、时长、分辨率；时长超过 90 秒、分辨率不是 720p 或未选最新文件时标出提示，由人工核验后标记完成。
- 轨迹文件即收集环节留存的待上传轨迹，不再单独填写；页面与提交表按 Windows 侧路径展示（`\\wsl.localhost\Ubuntu-24.04\...`），方便上传时在文件选择框中定位。
- 题目不再自行编号，提交表的序号就是出题时分配的甲方序号（见 5.1）。

### 5.9 提交表（页面）

- 提交表是单独的页面，顶部菜单「提交表」进入。页面工具栏可切换范围：「按状态」或「列表勾选的」（题目页列表里勾选的题目，没有勾选时不可选）；「按状态」旁边是与题目列表相同的状态多选下拉（不含自动做题的两项），默认只勾已完成，不勾选为全部状态，选择记在本机浏览器，改选时切回「按状态」（`/api/submission` 传 `statuses`，不传时只取已完成）；题目列表上方的「提交表」按钮也跳到这一页，有勾选时直接看勾选的，否则按状态。导出 Excel 与写入飞书都按当前页里的题目。每次进入或点「刷新」都重新读取，按甲方序号从小到大排列，没有甲方序号的排在最后。
- 工具栏「导出 Excel」按与当前页面相同的范围导出 xlsx（`/api/submission/xlsx`，openpyxl 生成，不依赖模板）：首行为提交表列名并冻结，序号与交付完整性按数字写入，其余按文本写入（长 ID 不变成科学计数法），快照链接可点击，长文本列自动换行；文件名为「提交表-时间戳.xlsx」。
- 语言/框架只写语言与主要框架或库的名字，不带版本号，英文小写，用英文逗号分隔（如 `java,python,nodejs`）：qa-gen 按此格式输出，入库、编辑保存与提交表展示时后端再统一规整（去掉版本号、中文说明与括号，`node.js` 记为 `nodejs`）。
- 每道题一块，按提交表列顺序展示：序号、分支、User Prompt、所属领域、子方向、任务类型、任务难度、语言/框架、Harness、Harness 版本、操作系统、环境可复现等级、初始环境快照、SessionID、TurnID/PromptID、轨迹文件、产物快照、运行录屏、交付完整性、Feedback、备注。
- 每道题一行可折叠：只有一题时默认展开，多题时默认折叠，工具栏提供全部展开、全部折叠；折叠时标题行仍可「复制整行」（不含序号、分支、备注三列，「复制表头」同样去掉这三列，粘贴后列对得上），标题行下方另起一行显示 User Prompt 的第一句（取第一个非空行到第一个句末标点，超过 80 字只截开头），展开后不再显示。
- 页面宽度随窗口放大（最宽约 1680px），工具栏吸顶，页面整体纵向滚动，内容自动换行；User Prompt、Feedback、备注占满整行。点击任一单元格复制该格内容，轨迹文件与运行录屏两格展示完整路径，点击时复制所在文件夹（带结尾反斜杠）；「复制整行」按制表符拼接（含换行的单元格加引号），可直接粘贴到表格；「复制表头」复制列名。
- 甲方提交标记：有甲方序号的已完成（或待返修）题在甲方平台提交后，点标题行的「标记已提交」；标记后标题行与详情顶部显示「甲方已提交」，题目列表序号下方显示「已提交」，未标记的显示「甲方未提交」；点「取消」可取消标记。详情页也提供「标记甲方已提交 / 取消甲方提交标记」按钮。
- 甲方序号：详情页「改甲方序号 / 填写甲方序号」可随时修改或补填（只能填一个数字，不能与其他未删除题目重复，留空清除；已标记甲方提交的题不能清除）。
- 返修过的题：标题行标出「第N轮返修」与改动格数，最近一轮返修改过的格高亮并标「已改」，悬停显示原值；「复制改动格」按提交表列顺序复制改过的格，每行为列名与新值（制表符分隔）。
- 写入飞书多维表格：
  - 目标表：配置页「飞书多维表格链接」指向的多维表格，表头同提交表（飞书字段名不能含 `/`，「语言/框架」「TurnID/PromptID」在飞书里是「语言|框架」「TurnID|PromptID」，按 `|` 对应 `/`），另有一列数字类型的 `UID` 存甲方序号。甲方序号是一道题全局唯一的 ID：飞书里按 UID 找记录，找到就更新，没找到就新增；流水线不另存飞书记录 ID，也不改表结构。
  - 写入时机：题目进入已完成（手动标记完成、自动录屏完成、返修完成且不需要重录）后，配置了表格链接且开着「完成后自动写入飞书」（默认开）时自动写入。提交表页每行标出飞书里有没有这条 UID（「飞书已写入 / 飞书未写入」，同一个 UID 有多条时标「飞书重复」），可以单独点「写入飞书 / 重写飞书」；工具栏「写入飞书」按当前页的范围一起写入。写入在后台执行（运行类型 `feishu`），运行记录挂在题目下，但不占题目互斥，失败只记在运行日志里，不改题目状态；所有写入串行执行，自动写入和手动写入同时触发时也不会重复新增。
  - 字段映射：以飞书表的真实字段为准，只填飞书里有、提交表里也有的列（序号、分支、备注不在飞书表时不填）；文本列填提交表展示的值，数字列转成数值，单选、多选填一个选项（选项不在飞书表里时报错，不自动加选项），公式、自动编号等只读列跳过；空值不写，更新时保留飞书里的原值。轨迹文件、运行录屏是附件列，上传本地文件（收集留存的 jsonl、完成录屏时选定的 mp4）；更新时飞书里已经是同名同大小的文件就沿用，否则先上传新文件再移除旧文件。
  - 实现：后端 `app/feishu.py` 负责映射与调度，经 `app/feishu_bridge.mjs` 调用 `plugin/feishu-table-tool`（用 WSL 中 `lark-cli` 已登录的用户身份，不保存 App Secret 或 token）。node 优先取 PATH，没有时取 nvm 安装的最新版本，`lark-cli` 取 node 同目录下的那个。

### 5.10 质检返修（skill `qa-rework`）

- 甲方质检结果分「不通过」与「待返修」。不通过的数据直接放弃，不进流水线；待返修的原因不固定，统一交给 AI 按质检原文直接处理，不按问题类型分流程，也不提供人工分步操作。
- **发起**：在已完成题目的「质检与返修」卡片粘贴一条质检原文（开头为【AI质检｜待返修】），点「AI 返修」。后端解析质检时间，以及问题、证据、修改建议三段（原文不分段时正文整体记为问题），连同当前提交内容快照（Feedback、评分、评分理由、备注、可复现等级、录屏步骤、产物快照、录屏文件、语言/框架）存入质检记录表 `qa_inspection`，题目进入「待返修」并立即启动 skill；同一题可多轮，按轮次保留。粘贴的是不通过的质检时直接提示放弃，不登记。
- **AI 处理**：后端把当前产物快照全新克隆两份：验收目录用于读代码与实测，修复目录只放对产物的修改。输入题目字段、本次与历次质检原文及当时的处理说明、当前提交内容、证据清单、提交记录与产物 diff、完整轨迹路径（质检中的「第N行」指该 jsonl 的物理行号）与轨迹摘要。skill 只针对质检指出的问题改：
  - Feedback 遵循 `style.md`，评分默认保持原分，备注与可复现等级在质检涉及时才改；
  - 质检要求补交文件或修正产物时，先在验收目录改好并实测，再把改动应用到修复目录（不放依赖、构建产物与截图）；返修补上的内容不算模型的产出；
  - 产物有改动或质检指出录屏问题时重写录屏前准备与录屏步骤，并标明需要重新录屏；
  - 输出几行处理说明，写明每条质检问题改了提交表的哪一列、产物改了哪些文件。
- **收尾**（后端自动完成）：
  - Feedback 规则检查不通过时，本次运行置为失败、提交内容不变，可重试重新跑 AI；
  - 修复目录有改动时按 5.5 的规则提交（标题 `fix: 返修 - <说明>`）并推送，更新产物快照，初始快照仍须是其祖先；
  - 产物有改动或需要重新录屏时进入待录屏，按录屏流程重录并标记完成后回到已完成；否则直接回到已完成。甲方序号沿用原值，本轮质检记为已返修。
- **提交表要改的格**：每轮对比本轮快照与改完后的内容（下一轮登记时的快照，最后一轮取当前内容），按提交表列顺序得出改动过的列，在该轮卡片中只列列名；新旧内容到提交表页中看，最近一轮改过的格在提交表页中高亮（见 5.9）。

### 5.11 全自动（补充题目池与自动做题）

两个开关的运行状态只保存在后端内存中，后端重启后都回到未开启；题目上的接管标记（`auto_run`）与停下信息（`auto_pause`）保存在数据库，重新开启自动做题后接着推进已接管的题。

**补充题目池**（批量出题页顶部卡片）：

- 自动出题暂不分配甲方序号，补充题目池暂停使用：点「补充题目池」只提示暂停使用，后端同样拒绝开始；已在运行的仍可停止。以下为恢复后的行为。

- 点「补充题目池」后一轮接一轮调用出题：每轮数量取配置（默认 10），子方向与难度由 AI 判断，技术栈偏好与补充要求为空；出完的题进入题目池（状态为待初始化、未被接管的题）。
- 再点一次只记下停止请求，不打断正在运行的出题，本轮结束后停止。
- 某一轮出题失败即终止，卡片显示错误与「查看出错日志」；连续两轮没有入库任何题目同样终止。卡片显示题目池数量、本次已完成轮数与入库题数、当前出题日志。

**自动做题调度**（题目页工具栏的「开始做题 / 停止做题」）：

- 开始前检查自动做题需要的工具（tmux、claude、Xvfb、xterm、xdotool、ffmpeg、node、全局 playwright 与 chromium、中文字体，录制声音时还有 pulseaudio），缺失时拒绝开始并给出安装方式。
- 调度器每 5 秒推进一次所有接管的题（按 id 从小到大）：

  | 状态 | 自动动作 |
  |---|---|
  | 待初始化 | 初始化并准备环境 |
  | 待准备环境（准备已跑完仍停在这里） | 停下，列出需要人工处理的项 |
  | 待做题 | 驱动 Claude Code 做题 |
  | 待收集 | 收集 |
  | 待验收 | 验收 |
  | 待查验 | 自动查验：通过则进入待录屏，否则停下 |
  | 待录屏 | 自动录屏，完成后标记完成 |
  | 失败 | 停下，按失败原因给出处理建议 |
  | 已完成 | 释放接管标记 |

- 节奏：准备线（待初始化、待准备环境，以及待做题但 Claude Code 还没发出 prompt 的）同时只有 1 道自动题；前一道题的 prompt 发出、Claude Code 开始做题后，就取下一道题开始初始化；人工「交给自动」的多道待初始化题同样按 id 排队，一次只开始准备一道（已接管但还没开始准备的题只是排队，不算占用准备线）。多道题的 Claude Code 会话并行做题，同时做题的会话不超过自动做题并行数（默认 10）。验收受 AI 并发上限约束；录屏同时只录 1 道。准备线空闲、做题会话未满且后段（待收集、待验收、待查验、待录屏）没停下的自动题少于积压上限（默认 10）时，从题目池按 id 顺序取下一道。任一环节出错只停下这道题等待处理，停下的题不占准备线、做题与积压名额，其他题照常推进，也照常取新题。
- 做完当前题后停止：不再从题目池取新题，已接管的题继续走完所有环节；全部完成（释放接管标记）或停下，且没有在跑的任务时自动关闭，停下的题保留接管标记待处理。未开启时点它，只推进已接管的题（如先「交给自动」的那道）；这种方式下点「继续取题」恢复正常取题。
- 停止：不再取新题、不再启动下一环节，正在跑的环节跑完为止，状态显示「停止中」直到这些环节结束。

**自动做题（Claude Code 驱动）**：

- 先关闭上次残留的同名做题会话（后端异常退出后 tmux 里可能还在跑），再处理做题目录：若有未作废的会话（上次自动做题中断或失败留下的），按重做处理：作废会话、恢复初始快照、重做次数加一。
- 在独立的 tmux 服务器（`tmux -L feedback`）中新建会话 `fbdo-<题目id>`，以 `env -i` 只保留新开 WSL 终端本来就有的环境变量（不带后端的虚拟环境），用 `bash -lic 'claude --dangerously-skip-permissions'` 启动。
- 识别启动界面：信任目录、bypass 模式确认这类确认框，按选项文字移动光标后回车；底栏出现 `bypass permissions on` 即就绪；超时或会话退出时失败并在日志中附上最后的屏幕。
- 以括号粘贴模式送入 prompt 原文（多行不会提前发送），再按回车；90 秒内必须出现首条输入与 prompt 原文一致的新会话文件（30 秒未出现时补按一次回车），否则失败。
- 轮询轨迹判断进度：主链最后一条 assistant 之后出现 `system/turn_duration` 记录、屏幕上没有 `esc to interrupt`、会话文件静止超过配置秒数（默认 30）才算做完；模型调用 AskUserQuestion 等待回答、超过做题超时（默认 240 分钟）都判为失败。
- 接口报错中断（主链最后一条是接口报错消息，如 504、529）：不输入「继续」，关闭会话，等待配置的秒数（默认 60）后按重做处理（作废会话、恢复初始快照）并重新启动会话做题；超过「接口报错自动重做次数」（默认 3，0 表示不自动重做）仍报错时判为失败。
- 做题过程中每 60 秒检查一次轨迹里的违规调用（子代理、MCP、非内置 skill），出现即判为失败，不等到做完再在收集时拦下。
- 做完后直接关闭会话，不再输入任何内容（避免轨迹里多出人工输入导致收集校验不过），题目进入待收集。
- 做题过程可在 WSL 终端用 `tmux -L feedback attach -r -t fbdo-<题目id>` 只读观看，详情的做题卡片给出该命令。

**自动查验**：沿用人工「通过」的门禁（交付完整性 1 到 5、可复现等级已选、Feedback 口吻与内容检查无问题），并要求录屏步骤非空、录屏步骤规则检查无问题、验收自检各项通过；全部满足即通过，否则停下并逐条列出问题，人工改完点「通过」或「重试」。

**自动录屏**（skill `qa-record`；试跑在 WSL 虚拟屏后台进行，正式录制默认在 Windows 本机桌面，画面与真人录屏一致）：

- 正式录制两种方式（配置「自动录屏在本机桌面录制」）：本机桌面（默认）在 Windows 主屏上用本机 Chrome、Windows Terminal 里的 WSL、真实的 Windows 文件对话框操作，录整个主屏（含任务栏）与系统声音，有真显卡；关闭时在 WSL 虚拟屏后台录制，不占用桌面。
- 每次录屏把产物快照全新克隆到录屏目录，起一块与本机主屏同尺寸的虚拟屏（Xvfb，WSLg 下 `/tmp/.X11-unix` 只读改用抽象套接字，加 `-noreset` 避免最后一个客户端断开时重置把根窗口指针变回 X 形）与一个只供本次使用的 PulseAudio 空设备（录制声音时），以新开 WSL 终端的登录环境执行录屏前准备（输出写入工作目录，进程组记录下来，录完一并结束）。主屏尺寸与工作区由 `app/wintools.py` 调 Windows 侧输入助手查询。
- 录屏脚本缓存在题目上，产物快照、录屏步骤、录屏前准备、执行器接口版本（`recorder.HARNESS_API`）都没变时直接复用；否则调用 `qa-record`：输入题目、Feedback、可录的证据、录屏前准备及其输出、录屏步骤、录屏目录、端口、屏幕与窗口尺寸、正式录制的环境、时长上限、脚本位置与试跑命令；skill 读产物代码写出 ES module 脚本，用试跑命令在虚拟屏上试跑（不录制）并核对截图，返回脚本、预计时长；无法自动录屏（正式录制也在虚拟屏且依赖真显卡无替代展示、需要外设或原生窗口、无法稳定复现）时返回需要人工录屏及原因。正式录制在本机桌面时，试跑看不到的真显卡渲染结果只在正式录制时检查。
- 试跑改变了服务与录屏目录的状态，生成脚本后执行收尾，正式录制前重新克隆、重新执行录屏前准备。
- 本机桌面的正式录制：同一时间只录一道题；先等桌面空闲（没锁屏，且配置的分钟数内没有鼠标键盘操作，默认 10 分钟），再克隆准备，准备完仍空闲才开录。系统记的「上次输入」也包括录屏自己注入的输入：最近一次输入不晚于上次录制结束、且上次没被人打断时，空闲从上次录制前的空闲起点算，连续录多道题不用每道都重新等。锁屏时桌面不再绘制、注入的输入也进不去，只能等解锁；屏保（恢复时不需要登录）不影响，屏保运行在单独的 Screen-saver 桌面上（不算锁屏，但注入的输入送不过去），执行器开录前结束屏保 .scr 连同它拉起的子进程（如 Wallpaper Engine 屏保的 `wallpaper64.exe -screensaver`；只结束 .scr 时系统停在屏保桌面不切回），等输入桌面回到 Default 再开始；初始化中途出错也会关掉已打开的窗口。录制中输入助手用低级钩子监听，出现不带注入标记的鼠标键盘事件（真人操作）立即中止、收尾，等再次空闲后重来，超过配置的重录次数（默认 3）报错停下；其他程序的弹窗照常录，不中止。录制期间开系统勿扰（只允许闹钟），其他程序的通知不弹出来挡画面（照常进通知中心），录完恢复原来的设置；输入助手意外退出没来得及恢复的，下次启动时恢复。
- 执行器（`app/record_harness/`）：`harness.mjs` 提供公共的 ctx 接口与录制合成流程，`human.mjs` 生成人手式的指针轨迹（弧度、先快后慢的最小加加速度曲线、细微抖动、远距离偶尔略过再拉回，约 10 毫秒一个点）与打字节奏（几个字一组、有快有慢、空格后偶尔停顿），落点在元素中心附近随机，点击按下与松开有间隔；刷新是点刷新按钮，打开网址是在地址栏打字，上传是在弹出的文件对话框里选文件，原生下拉框是点开后指针移到列表里的目标项上点击（本机桌面按弹出列表窗口的位置与行数算出目标行；虚拟屏或列表超过 20 行要滚动时用方向键一格一格移过去再回车，不一下跳到目标项），终端命令逐字打出后回车、靠提示符钩子写出的退出码判断结束。两个平台后端：
  - `backend-x11.mjs`（试跑与虚拟屏录制）：有界面的 chromium（单独的配置目录与 GTK 设置：Windows 样式指针、中文界面、关闭翻译、对话框自带标题栏，文件对话框默认打开录屏目录）与 xterm（Windows Terminal 的 Campbell 配色与字体），xdotool 驱动；`app/wincursor.py` 生成 Windows 样式的 X 光标主题，fontconfig 使用 `/mnt/c/Windows/Fonts` 的 Windows 字体；GTK 文件选择框摆到屏幕中间后输入相对路径回车。录制时画面与声音分两个 ffmpeg 进程（同一进程读 pulse 会拖住 x11grab），都保留墙钟时间戳。
  - `backend-win.mjs`（本机桌面录制，执行器在 Windows 的 node 里运行）：本机 Chrome 以单独的配置目录（`%LOCALAPPDATA%\feedback-record\chrome-profile`，关闭翻译与登录提示，文件对话框默认打开暂存目录）正常启动，只多一个远程调试端口，执行器用 playwright-core 的 connectOverCDP 读页面状态，结束时发 `Browser.close`；Windows Terminal 新窗口里运行 `wsl.exe --cd <录屏目录> bash --rcfile`；`wininput.py`（Windows Python，ctypes）用 SendInput 注入鼠标键盘（带注入标记）、查窗口与 Chrome 网页内容区位置、切前台（两个窗口之间用 Alt+Tab）、保持屏幕常亮、开关勿扰（系统 QuietHoursSettings 接口）、监听真人操作；上传时把文件复制进「下载\<分支名>」（对话框打开在这里），`uia_find.ps1`（Windows PowerShell 的 UI 自动化，脚本带 UTF-8 BOM）找到文件列表项「名称」一格的位置后指针移过去双击，找不到时退回在文件名框输入文件名回车，录完删掉复制的文件；画面用 ffmpeg 的 gfxcapture（Windows.Graphics.Capture，指针由系统合成，ddagrab 画自定义指针会带白框）按墙钟时间戳录主屏，声音用 `winaudio.py`（pyaudiowpatch 的 WASAPI 回环，同时往默认输出写静音保证回环连续出数据）录系统声音并报告起始墙钟时刻，网页出声约晚 110ms，补回 60ms。
  - 合成：按两路起始时刻对齐，声音晚开始就在前面补静音、早开始就裁掉开头，画面按屏幕原尺寸录，合成时按比例缩到 720p（1920x1080 的屏幕得到 1280x720），压成 30 帧 mp4，时长受配置上限约束（默认 90 秒）；截图只在试跑与出错时截。
- 录完执行收尾并清理虚拟屏、声卡与服务进程；用 ffprobe 校验时长不超过上限、分辨率是屏幕按比例缩到 720p 的尺寸，合格后移到待上传文件目录（文件名为「甲方序号-分支名.mp4」，与轨迹同名，重录时覆盖），标记完成。
- Windows 侧依赖由 `scripts/setup-desktop-record.ps1` 安装（playwright-core 装在 `%LOCALAPPDATA%\feedback-record\node`，pyaudiowpatch 装进用户目录），另需 Chrome、Windows Terminal、ffmpeg（含 gfxcapture）、Python、node；自动做题开始前与每次录屏前检查。

**停下与处理**：

- 停下信息记录环节、原因、逐条处理建议、出错的运行与时间；详情顶部红框显示，并提供「查看日志」「重试」「转人工」，录屏环节另有「重新生成录屏脚本并重试」。
- 待准备环境但没有待处理项（准备中途被打断，如后端重启）时不停下，直接接着准备。
- 调度器单次推进出错时工具栏显示「调度出错」，之后推进成功即清除。
- 处理建议按失败原因匹配（codex 认证或限流、轨迹校验不通过建议重做、Claude Code 接口报错（含自动重做后仍报错）、做题中出现违规调用、模型提问、启动卡住、录屏前准备失败、需要人工录屏、录屏脚本执行失败等），没有命中时按环节给出默认建议。
- 重试：失败的题按失败前的状态重试（做题环节回到待做题，由调度器作废残留会话后重新做题）；待准备环境重新准备；待查验重新检查；待录屏重新录制。
- 人工在详情里执行原有操作（继续准备、重做、通过、打回、标记完成等）时自动清除停下信息，自动流程从新状态接着走；「转人工」退出自动流程，之后完全按手动流程；未完成的题可点「交给自动」由调度器接管。
- 题目有任务在运行时，不允许执行只改状态的人工操作（做题完成、通过、打回、标记完成），避免与自动流程抢状态。

## 6. 口吻控制

- `style.md` 规定：
  - 平实直接，像懂行的人对这次任务的直接判断；不套固定开头（如每篇都以「我让模型做某事」开头），直接从最关键的事实写起，写模型的操作用「模型」，写自己实测的现象可以用「我」；不用审稿模板与质检口吻（评审方、本轮任务、验收结论、固定分栏等）；不使用 markdown；
  - 用空格代替标点，中文标点一律禁止；
  - 英文全部小写，包括文件名、报错、命令（如 `date.py`、`valueerror`、`readme.md`）；
  - 文件名、路径、版本号、命令、数值中英文词内部的 `.` `/` `-` `_` `:` 允许保留（如 `src/utils/date.py`、`v22.23.2`、`-16lufs`）；
  - 中文与英文、中文与数字之间不加空格；断句用的空格可以紧挨英文或数字，但英文或数字两侧不能同时加空格（如「我点了 play 按钮」）；
  - 禁止「首先」「其次」「综上」「值得注意的是」等书面化或 AI 化表达；
  - 过程、产物、证据、原分四件事都要写并互相对上：过程取自轨迹中真实发生的操作与验证；产物写最终提交的问题或确实完成的依据，区分中间版本与最终提交；1 到 4 分的每个产物问题写出代码锚点（文件、函数、尽量带行号）、代码原因、业务影响和最终状态；结尾写明「给N分」并由前文事实支撑；5 分写出具体模块与验证结果，不硬编缺点；
  - 篇幅：一般 150 到 300 字，不超过 400 字；1 到 4 分只写一个最关键的过程问题和一到两个影响最大的产物问题，每个产物问题一个代码锚点，做对的部分不写，不写成问题清单；
  - 列明会被打回的写法：只有现象没有过程、只有过程没有产物、只有文件名没有代码原因、代码原因只在评单里、占位指代、没执行的断言写成通过、夸大数量、把已修复的中间失败写成最终失败、把网络与平台问题算成模型问题、把工具链或 shell 环境噪声（如 git bash 路径转换）算成模型的过程问题、可套用到任何任务的空话。
- Codex 工作区的 `AGENTS.md` 规定：本目录为自动化流水线，最终回复只输出符合 schema 的 JSON，字段内容只遵循 `style.md`，不添加称呼或额外说明；并写明 5.6 的权限边界。Windows 全局 `~/.codex/AGENTS.md` 仍会被加载，由该文件覆盖其输出要求。
- 后端对 Feedback 做规则检查：markdown 结构、中文标点、独立的英文标点（不在英文词内部的符号）、大写字母、英文或数字两侧同时加空格、禁用词；另做内容门禁：结尾须有「给N分」且与交付完整性一致、至少有一个代码锚点（带扩展名的文件，可带行号）、不含占位指代与模板空话（见原文、同上、评审方、本轮任务、整体表现不错、仍有提升空间、建议修复、还需修复等）、不以「我让模型」这类固定开头起笔、不含工具链噪声归因（git bash、msys、路径转换）、篇幅不超过 400 字；不通过时页面标红且不能标记为通过。
- qa-review 输出的自检包含过程、产物、代码锚点、原分依据四项，页面逐项标出。
- prompt 允许保留正常标点与代码片段；语气平实克制，不刻意模仿口语，不用「烦死了」「很爽」「绝了」等情绪化或网络化词汇（规则写在 qa-gen skill 中）。开头直接说要做什么，在「我在做一个……」「我想做个……」「帮我做一个……」中轮换；不写做题环境的套话（从空仓库、Ubuntu、WSL、Windows 浏览器访问 localhost、不用 Docker 等），只有属于需求本身的约束（如要能离线用、只能用标准库）才用这道题自己的话写。后端检查 AI 化表达、刻意口语词表、环境套话与开头说法，命中时页面标红提示。

## 7. 网页功能

- 页面布局：左侧题目列表、右侧题目详情，两侧各自滚动；题目列表可向左折叠，折叠后只显示题目名与状态，折叠状态在本机记住；运行日志以底部抽屉展示，打开时两侧面板自动让出高度；每个运行一个标签（圆点标出运行中、成功、失败），运行中的标签都在后台持续读取，可切换查看、单独关闭或全部关闭，「停止」作用于当前标签；顶部导航的「日志」按钮可随时手动打开，把所有运行中的运行补成标签，没有运行中的时打开最近一次运行。
- 题目列表：按状态多选筛选（下拉面板里勾选各状态以及「自动做题中」「自动需处理」，题目满足任一勾选项即显示，不勾选为全部状态，选择记在本机浏览器），按甲方序号从大到小排列（没有甲方序号的排在最后），显示甲方序号（已标记甲方提交的在下方标「已提交」）、分支名与子方向、难度、状态（需人工处理的阶段醒目标出）、「今日必须提交」标记、更新时间与做题完成时间。
- 题目详情：顶部为分支名、状态、流水线进度轨（初始化 → 已完成八个阶段，失败时标红所在阶段）与操作按钮（初始化并准备环境、继续准备、重做、收集、验收、准备录屏环境等）；下方按题目信息、素材、环境检查、做题、收集结果、验收与 Feedback、录屏、运行记录分区。所有字段统一为「左标签、右控件」的同一网格，控件宽度一致。每张卡片可折叠，按当前阶段默认展开相关卡片，展开状态在本机记住，并提供全部展开、全部折叠；验收要点、环境需求、检查清单、轨迹摘要、证据清单等大段内容默认折叠，检查有不通过项时自动展开；命令类内容右上角带一键复制。
- 批量出题页：顶部为「补充题目池」卡片（见 5.11）；下方为手动出题表单，所属领域固定显示为「游戏、图形与多媒体」，必填甲方序号（输入时提示将出几道题与展开后的序号），可选子方向、难度、技术栈偏好、补充要求。
- 自动做题：题目页工具栏有「开始做题」，运行中换成「做完当前题后停止」与「停止做题」（做完当前题后停止时另有「继续取题」），旁边显示做题线当前的题、后段数量与积压上限、需处理数量（点击筛出）与题目池数量；状态筛选增加「自动做题中」「自动需处理」；列表行标出「自动」「需处理」；详情的做题卡片给出只读观看命令，录屏卡片可折叠查看自动录屏脚本。
- 配置页：GitHub 仓库地址与凭据、codex 可执行文件路径、Codex 工作区路径、模型名、推理强度、是否沿用 config.toml 的供应商与模型、config.toml 路径（留空自动定位）、WSL 发行版名、并发数、单次运行超时、连续重连上限、验收端口范围；补充题目池每轮出题数、自动做题并行数、自动做题后段积压上限、待上传文件目录、自动确认显卡能力（默认开启）、等待 Claude Code 就绪秒数、单题做题超时、做完判定的静止时长、接口报错自动重做次数与等待秒数、自动录屏时长上限、自动录屏是否录制声音。
- 提交表页：顶部菜单依次为题目、提交表、批量出题、配置、日志；提交表页见 5.9。
- 质检与返修卡片：已完成题目和有质检记录的题目在详情顶部显示，每轮质检一张可折叠的卡片（默认只展开最近一轮，展开状态在本机记住），标题行为轮次、处理状态、质检时间与改动格数，展开后依次为这一轮提交表要改的列名、质检原文、AI 处理说明；已完成时提供质检原文输入框与唯一的「AI 返修」按钮。待返修时进度轨在已完成之后追加「返修」一段。

## 8. 出错处理

- skill 运行失败（codex 非零退出、超时、额度限流、认证失败、最终输出不符合 schema）：题目置为「失败」，保留日志，可重试。限流与认证失败只按 stderr 和 codex 自身的错误事件判断，不看模型执行命令的输出；状态码 401、429 按整数匹配。
- 连不上供应商时 codex 不退出、反复发出 `Reconnecting...` 错误事件：连续达到「连续重连上限」（默认 10，0 表示不限制；中间出现其他事件即重新计数）时结束 codex 进程（含 Windows 侧残留），题目置为「失败」并提示检查网络或供应商地址。
- 沿用 `config.toml` 时，文件读不到、不是合法 TOML、指定的供应商缺少 `[model_providers.<名称>]` 一节（内置的 openai、ollama、lmstudio、oss 除外），都在启动前失败并给出文件路径。
- codex 在 stderr 输出的 `failed to write models cache` 属于本地缓存文件只读导致的提示，不视为失败。
- 同一题目同一时间只允许一个任务运行；全局并发上限默认 2，可配置；并发验收的题目使用互不重叠的端口段。
- 推送失败、轨迹定位失败、校验不通过、远端分支被改写：在页面明确显示原因，不推进状态。
- 数据库每日备份到 `data/backups/`，保留最近 14 份。

## 9. 测试

- 执行环境冒烟（新环境部署后、每次升级 codex 或调整配置后重跑 `scripts/smoke-codex.sh`）：
  - WSL 通过互操作调用 Windows codex，`--json` 事件流可逐行读取；
  - 运行后 `codex login status` 仍为原登录方式，`auth.json` 未被改写，`~/.codex/sessions` 无新增文件；
  - 打印实际使用的模型与供应商参数（与正式运行共用 `codex_runner.model_args`），沿用 `config.toml` 时同时打印文件路径；
  - `'$<skill>'` 能触发 `.agents/skills/` 下的 skill，stdin 内容可读到，`-o` 输出符合 schema；
  - skill 内 `wsl.exe ... bash -ic 'node -v'` 能拿到 WSL 的 node 版本，`\\wsl.localhost\...` 路径可读（符号链接无法经该路径读取，探测用用户目录下的普通文件）；
  - WSL 中 `git ls-remote` 与 `ssh -T git@github.com` 可通。
- 轨迹解析：以已有真实轨迹 jsonl 作为样本，覆盖单轮校验、「继续」识别、作废会话排除、模型比对、字段提取、污染检测、摘要生成。
- 快照逻辑：在临时 git 仓库中覆盖孤儿分支创建、重做重置、被忽略新文件补交、远端被推送或强推的检测、祖先关系校验。
- 口吻检查：单元测试覆盖中文标点、英文词内部符号放行、独立英文标点、大写、中英文间空格、禁用词。
- 甲方序号：批量写法解析（分隔符、区间、重复、越界、格式错误）；出题按顺序分配、数量取序号个数、未填与已占用时拒绝；详情修改与补填的唯一性；列表与提交表按甲方序号排序；甲方提交标记与取消；迁移去掉自编序号列并建甲方序号唯一索引。
- 提交表：核对列顺序、序号取甲方序号、轨迹文件取收集留存的轨迹、未勾选时只列已完成题目；录屏文件按修改时间取最新。
- 写入飞书：按假字段表核对映射（`|` 对应 `/`、选项包成数组、数字转数值、附件取 WSL 路径、只读列与空值跳过、对不上的列列出）；没有甲方序号或飞书表没有 UID 列时拒绝；只在配置了链接且开着自动写入时触发，完成操作不受写入失败影响；写入失败不改题目状态、不占题目互斥。真实飞书表上验证过新增、更新时附件沿用、换附件时先传后删。
- 质检返修：质检原文解析（AI 前缀与旧写法、分段与不分段、多条混贴、无结论、不通过直接拒绝）；用假的 codex 结果走一遍 AI 返修（直接回到已完成并列出要改的格、甲方序号与录屏沿用）；修复目录有改动时推送新快照并回到待录屏；Feedback 规则检查不通过时失败并可重试；修复目录的提交标题、被忽略文件补交与依赖目录排除；qa-rework schema 的可复现等级与 `pipeline.REPRO_LEVELS` 一致。
- 语言/框架规整：去版本号、中文说明与括号，逗号分隔；提交表展示与编辑保存。
- 数据库迁移：新库由初始化脚本直接建出最新结构；存量库补执行缺的增量脚本。
- 全自动：轨迹进度判断（运行中、做完、接口报错、提问、子代理记录不影响主链）；确认框按键计算；补充题目池连跑后按停止在本轮结束、失败即终止、连续空轮终止、接口暂停开始；调度器按 id 取题、Claude Code 开始做题后才准备下一道、交给自动的多道待初始化题按准备线排队、残留做题会话先关闭再恢复初始快照、做题会话上限、积压上限、失败与待准备环境只停下这道且不挡取新题、自动查验通过与停下、录屏同时 1 道、已完成释放；人工操作清除停下信息、重试与重新生成录屏脚本、转人工与交给自动；工具缺失时拒绝开始；录屏脚本缓存键、录屏文件校验、qa-record schema 严格；数据库迁移补齐新字段。
- 全自动冒烟：虚拟屏上用执行器跑一段页面点击加终端命令的脚本并正式录制，核对 1280x720 mp4 与画面、录完服务进程被清理；Claude Code 驱动在临时目录启动到就绪（自动确认信任目录）后关闭。
