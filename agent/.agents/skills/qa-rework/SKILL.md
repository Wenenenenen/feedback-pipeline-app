# qa-rework 按质检原文返修

## 输入

`<stdin>` 中给出：题目字段与 User Prompt 原文、内部验收要点、本次质检原文、历次质检及当时的处理说明、当前提交的内容（交付完整性、环境可复现等级、评分理由、Feedback、备注、录屏步骤）、验收时的证据清单、初始快照与当前产物快照、提交记录、产物 diff、验收目录、修复目录、执行命令方式、可用端口段、录屏环境（录屏目录与录屏命令写法）、完整轨迹路径与轨迹摘要。

开始前先读本目录的 `AGENTS.md`（权限边界、WSL 命令写法）与 `style.md`（Feedback 写法）。

## 原则

- 这是返修不是重新验收：只针对质检指出的问题改，质检没有质疑、且你核实后仍然成立的内容保留原样，不顺手改写别的地方，也不引入新的问题点。
- 质检的问题类型不固定，按原文逐条理解后直接处理，不向人提问。
- 历次质检里已经处理过的问题，这次改动时不能让它重新出现。

## 步骤

1. **拆质检**：把本次质检的问题、证据、修改建议拆成独立的问题条目。
2. **核对依据**：
   - 质检引用的「原轨第N行」是完整轨迹 jsonl 的物理行号，用 `wsl.exe -d <发行版> -- sed -n 'Np' <轨迹 WSL 路径>` 读取原行核对；「第N次工具调用」对照轨迹摘要和完整轨迹核对；
   - 质检引用的代码、文件、测试，在验收目录中读代码或实测核对；
   - 质检明确判定为环境、工具链或平台噪声的内容（如 shell 路径转换、网络、代理），一律从 Feedback 中删除，不再算作模型的问题。
3. **改提交内容**：
   - Feedback：在当前内容上修改，满足质检的修改建议，同时严格遵循 `style.md`，过程、产物、证据、原分四件事仍要齐全并互相对上；新写进去的事实必须是你核实过的，代码原因写在 Feedback 原文里；
   - 交付完整性：默认保持原分；只有质检明确指出原分依据不成立，或核实后前文事实撑不起原分时才调整；
   - 备注、环境可复现等级：质检涉及时才改，否则原样返回。
4. **改产物**（质检要求补交文件或修正产物时才做，否则修复目录保持原样）：
   - 先在验收目录里改并实测，确认问题解决；
   - 再把同样的改动应用到修复目录：只放源码、测试、素材等应进入产物的文件，不放依赖目录、构建产物、截图和验证用的临时文件，也不要在修复目录里安装依赖或运行构建；
   - 需要的文件可以从做题目录（只读）或验收目录复制；
   - 不要在修复目录里执行 git 命令，后端会把修复目录的改动提交并推送为新的产物快照（提交标题以 `fix: 返修` 开头）；
   - 这些修改是返修补交的，不是模型的产出：Feedback 评价的仍是模型在轨迹中的过程与产出，不能把返修补上的内容写成模型做到的。
5. **录屏**：
   - 修复目录有改动时，按改动后的产物重写录屏步骤（要求同 qa-review：90 秒内、从干净克隆开始、失败项也要录），`need_rerecord` 设为 true；
   - 产物没改但质检指出录屏有问题时，同样重写录屏步骤并把 `need_rerecord` 设为 true；
   - 其余情况录屏步骤原样返回，`need_rerecord` 为 false；
   - 录屏步骤的写法按输入「录屏环境」：人在录屏目录的 WSL 终端里照着粘贴执行，命令用相对路径，不加 `wsl.exe`、`bash -ic` 包装，不出现验收目录、修复目录的路径；每个操作人工几秒内能完成，不要求点精确的像素坐标，必须定位像素时给出可粘贴的浏览器控制台脚本；原样返回的步骤不符合这些要求时只改写法，`need_rerecord` 不因此改变。
6. **处理说明**：`summary` 用几行简短说明本次怎么处理的，每条质检问题一行，写改了提交表的哪一列、产物改了哪些文件；核实后与质检结论不一致或处理不了的，也在这里写明依据。
7. **自检**：`self_check` 按最终 Feedback 原文如实填写，含义同 qa-review；任一项为 false 时先改 Feedback 再输出。写完逐条对照 `style.md` 的「一定会被打回的写法」自查。

## 输出

按 schema 输出 JSON，没改动的字段原样返回当前提交的内容。
