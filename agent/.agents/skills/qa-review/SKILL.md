# qa-review 验收与写 Feedback

## 输入

`<stdin>` 中给出：题目字段与 User Prompt 原文、内部验收要点、环境检查结果、出题备注草稿、验收目录（WSL 路径与 Windows UNC 路径）、执行命令方式、可用端口段、录屏环境（录屏目录与录屏命令写法）、完整轨迹 UNC 路径、轨迹摘要、产物 diff、人工意见（打回时）。

开始前先读本目录的 `AGENTS.md`（权限边界、WSL 命令写法）与 `style.md`（Feedback 写法）。

## 步骤

1. **读需求**：逐条拆出 prompt 中的明示需求，加上内部验收要点与素材包里的约定文件（如 `约定.json`、样例格式说明），形成核对清单。产物问题只能是对这份清单的违背，或者正常操作下就会出现的实际错误（崩溃、报错、NaN、白屏、数值算错、页面显示与内部状态不一致）；清单里没有的期望不能写成缺陷：
   - 题面没要求的功能不算缺失，例如只要求导出 JSON 时，不能要求导出的 JSON 还能导回；
   - 导入非法文件时，题面只要求指出不合法的项，就不能要求保留上一份规则或结果；只有报错没指出是哪一项、界面还显示旧内容却已不能操作这类实际错误才算问题；
   - 拿不准某个期望是不是题面要求时，回到 User Prompt 原句和约定文件核对，找不到依据的不写进 Feedback。
2. **读过程**：看轨迹摘要，必要时按完整轨迹路径检索细节（工具调用、报错、模型最终回复里宣称做了什么）。重点找：
   - 宣称完成但实际没做或做错（虚假成功）；
   - 改完没运行验证就说完成、对报错视而不见；
   - 同一失败操作反复重试、规划混乱、目标漂移；
   - 违反 prompt 约束（擅自换技术栈、用了明确禁止的库）；
   - 编造不存在的 API、文件或参数。
   同时记下模型实际执行过哪些验证（哪条命令、哪个测试文件、跑了几轮、结果如何），以及哪些需求从头到尾没验证过；数量以轨迹为准，不夸大。中途失败、后来修好的问题要标明是中间版本的，不能当成最终产物的问题。网络、api、代理、网关、平台超时和工具重跑不算模型的过程问题；git bash 路径转换、msys 路径改写这类工具链或 shell 环境噪声也不算，模型对这类现象的判断不能拿来评价它的方案。
3. **读产物**：通过 UNC 路径读代码，结合 diff 核对每个需求点是否真正实现，找 stub、todo、硬编码、假数据、被删改的测试。实测发现的每个问题都要回到最终提交的代码里定位根因：哪个文件、哪个函数、第几行，那段逻辑具体怎么错了；定位不到代码原因的现象，不能只凭现象写进 Feedback。
4. **实测**：在验收目录中按项目自身说明安装依赖、构建、运行测试、启动程序。
   - 所有命令按输入中「执行命令方式」给出的写法执行（形如 `wsl.exe -d <发行版> --cd <验收目录> -- bash -ic '<命令>'`）；
   - 服务只用分配的端口，后台启动并在验证后结束；
   - 网页或画面类：用 playwright（`npx playwright screenshot` 或 node 脚本）打开页面截图，截图保存到验收目录 `.qa/` 下并在证据中写路径；
   - 音视频类：用 `ffprobe` 检查编码、分辨率、时长、码率，用 `ffmpeg -af ebur128` 等检查响度，用实际文件验证；
   - 依赖显卡、无头浏览器无法验证的项（如 WebGPU 渲染效果），证据中 `needs_recording_confirm` 设为 true，留给录屏确认；
   - 工具缺失（如没装 ffmpeg 或 playwright）时，在证据中如实记录「验收环境缺少某工具 未能验证」，不得臆测结果，也不要把它算作模型的问题。
5. **评分**：按下表给交付完整性 1-5 分，`score_reason` 引用证据编号或具体现象说明理由。

| 分 | 标准 |
|---|---|
| 5 | 一次性跑通，所有明示需求实现，并主动处理了隐性需求，零虚假成功 |
| 4 | 主要需求全部达成，可运行，只有极少细节遗漏，无虚假成功 |
| 3 | 核心功能可跑，但有明显 bug 需人工修；或有轻微虚假成功 |
| 2 | 主要需求未达成，因逻辑或依赖问题无法运行；或较大比例虚假成功 |
| 1 | 完全不可用、严重编译报错、答非所问，或极其恶劣的虚假成功 |

6. **写 Feedback**：严格遵循 `style.md`，用一段自然的话写完。5 分写做好了什么，1 到 4 分只写没做好什么；不要以「我让模型做某事」开头，也不先复述需求，直接从最关键的事实写起。四件事都要落地并互相对上：
   - 过程：模型做了什么、怎么验证的、漏验了什么，只写轨迹里真实发生的事；
   - 产物：最终提交里还有什么问题，或者为什么确实完成；1 到 4 分时每个产物问题都写出代码锚点（文件、函数，尽量带行号）、代码原因、业务影响，并说明问题在最终提交里仍然存在；
   - 证据：只用自己核实过的事实，没执行的断言不能写成测试通过；代码原因必须写在 Feedback 原文里，不能只留在证据清单或评分理由中；
   - 原分：结尾写明「给N分」，N 与 `delivery_score` 一致，并让前面的事实撑得起这个分数；5 分不硬编缺点，但要写出具体对象和验证结果；
   - 写短：按 `style.md`「篇幅与取舍」，一般 150 到 300 字，不超过 400 字；1 到 4 分只写一个最关键的过程问题和一到两个影响最大的产物问题，每个产物问题一个代码锚点，其余问题不写进 Feedback（留在证据清单里即可）；做对的部分不写；
   - 选问题：影响相近时，优先写在产物页面上用正常操作（点按钮、选素材、输参数）就能看到的问题，这样录屏能直接展示；要专门构造输入或注入脚本才能触发的问题，除非是最关键的，否则只留在证据清单；
   - 只写模型能力造成的问题，环境、网络、验收工具缺失不写进 Feedback；
   - 有人工意见时，按意见调整。
   写完逐条对照 `style.md` 的「一定会被打回的写法」自查，命中任何一条就重写。
7. **录屏步骤**：录屏只录产物上的问题，启动和结束服务不录。录屏目录是产物快照的全新克隆（不含依赖），人在 WSL 终端里先 cd 到输入「录屏环境」给出的录屏目录，浏览器用 Windows 本机浏览器。输出分三部分：
   - `record_prep.setup`：录屏前在录屏目录终端粘贴执行、不录：安装依赖、构建、后台启动服务（输出写到 `.qa/` 下的日志，PID 写到 `.qa/record.pid`），最后用 `echo` 打出访问地址；
   - `record_steps`：真正录制的部分，总共 1 到 3 步，60 秒左右，最长不超过 90 秒。第一步直接打开产物页面并操作出第一个问题，Feedback 中的每个产物问题各一步（失败项照录，把报错过程录出来），5 分时录核心功能跑通的一步；
   - `record_prep.cleanup`：录完后执行、不录：结束服务（如 `kill "$(cat .qa/record.pid)"`），没有后台服务时为空字符串。

   录制部分的要求：
   - 证据放在产物页面上、放在操作上：用页面上能看到的按钮、下拉框、输入框、滑块、导入按钮等正常操作把问题做出来，`expect` 写页面上看得见的现象（报错提示、数值、画面变化）；产物本身是命令行工具时，执行产物自己的命令就是操作；
   - 不在录屏里跑脚本复现：不写 heredoc、python 或 node 临时脚本，不在录屏时生成或改造文件，不用控制台脚本注入数据、改页面状态或拦截函数；能用素材里现成的文件和正常操作展示的，一律用正常操作；
   - 问题确实要特殊输入文件才能触发时（如截断的录音），在 `record_prep.setup` 里生成到录屏目录的 `.qa/` 下，录屏时用页面自带的导入按钮或拖放，在文件选择框里按「录屏环境」给出的 Windows 访问路径选中它；
   - 控制台脚本只在必须定位到精确像素、且页面没有其他入口时才用，只读（如 `getImageData` 读像素值），保持一行，能看出在做什么；其他用途（导入数据、改参数、调用页面函数、读别的数值）一律改成页面上的正常操作，自动查验会拦下；不要求人点精确的像素坐标、精确拖动或定时操作；
   - 每步给出 `action`（一句话说清做什么，按画面上可见的文字描述界面操作，不写预估秒数）、`command`（要粘贴的浏览器地址、输入框里要填的值或产物命令，纯点击操作时为空字符串）、`expect`（画面上应该看到什么）；
   - 命令只用录屏目录下的相对路径，不加 `wsl.exe`、`bash -ic` 包装，不出现验收目录、修复目录的路径；
   - 只录 Feedback 里写到的内容，不为证据清单里没写进 Feedback 的问题单独加步骤，不录测试脚本的输出。
8. **其他字段**：
   - `reproducibility`：环境可复现等级，只能三选一，原样填写：
     - 「无外部依赖」：产物不依赖需要另行安装的包、外部服务或外网资源，克隆后用现有运行时即可启动；
     - 「有外部依赖，未容器化」：需要安装依赖包、系统工具（如 ffmpeg）、数据库或访问外部站点，且没有可用的容器化配置；
     - 「已容器化，可一键起环境」：产物自带 Dockerfile 或 compose 等配置，并且验收时实测一条命令能拉起完整环境；
     素材已随初始快照提交的不算外部依赖；
   - `lang_framework`：按最终提交的源码树填写语言/框架，输入里出题时的预估只作参考：
     - 只写产物里真实存在的源码语言与实际引入的框架、库、浏览器 API（如 `JavaScript, HTML, CSS, Canvas 2D`、`Python, FastAPI, NumPy`），用官方大小写，英文逗号加空格分隔，不带版本号和说明文字；
     - 只用来起静态服务（如 `python3 -m http.server`）或只在 README 里提到的工具不算；有 `.py` 测试或素材脚本并且进了产物提交的才写 Python；
     - 依据是产物的文件树、依赖清单（package.json、requirements.txt、pyproject.toml 等）和源码里的 import；
   - `remark`：在出题备注草稿基础上补充（如中断与「继续」说明、录屏注意事项），保持简短；
   - `self_check`：按 Feedback 原文逐项自查后如实填写，任何一项为 false 都应先改 Feedback 再输出：
     - `has_process`：写了模型实际做了什么、验证或漏验了什么；
     - `has_product`：写了最终提交的问题或确实完成的依据，并区分了中间版本与最终提交；
     - `has_code_anchor`：问题落到了文件、函数或行号，并写出了代码原因（5 分时写到了具体模块和验证结果）；
     - `score_consistent`：结尾的「给N分」与 `delivery_score` 一致，且前面的事实撑得起这个分数（写了核心需求未实现或无法运行却给 4 到 5 分，或者写了全部达成却给 1 到 2 分都算不一致）；
     - `note`：一句核对结论。

## 输出

按 schema 输出 JSON。证据清单至少覆盖每个明示需求点各一条。
