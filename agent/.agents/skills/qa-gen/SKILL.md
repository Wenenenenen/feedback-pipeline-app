# qa-gen 批量出题

## 输入

`<stdin>` 中给出：数量、所属领域、子方向（可能由你选择）、难度（可能由你判断）、技术栈偏好、补充要求、领域与子方向表、库内已有题目列表。

开始前先读本目录的 `banned-topics.md` 与 `AGENTS.md`。

## 出题要求

1. **类型**：全部是 0-1 功能开发（从空仓库做出一个完整可运行的项目），`task_type` 固定为「功能开发」。
2. **领域**：`domain` 与 `subdomain` 必须原样取自输入中的领域与子方向表，不得简写或改写（例如必须写「音视频处理」，不能写「音视频」或「多媒体处理」），且子方向必须属于所选领域；子方向优先用明确列出的重点方向，「其他」只在确有跨方向混合时使用。
   - 「游戏、图形与多媒体」下「音视频处理」「图形渲染」是重点方向，「游戏开发」「图像处理」同样可选；
   - 「游戏开发」：游戏规则与关卡机制、数值与战斗系统、AI 行为、联机服务端、引擎工具链等真实工程；客户端优先做成浏览器可运行的网页游戏，或命令行、服务端程序，不得依赖 Unity、Unreal 等需要编辑器或商业授权的引擎；
   - 「图像处理」：传统图像增强与校正、抠图与合成编辑、拼接融合、图像编码格式与压缩、画质评估等，核心算法要自己实现，不能只是调用现成库的一行接口。
3. **难度**：只出「困难」「地狱」，按 `banned-topics.md` 的定义自评；不得满足「过于简单」的任何两条特征。题目要有真实的设计取舍、隐藏的边界条件或复杂状态，而不是功能堆砌。
4. **查重**：不得与 `banned-topics.md` 中的题目雷同，不得与输入中的已有题目在「项目 + 需求」上雷同；`similarity_note` 用一句话说明与最接近的已有题目差在哪里，没有接近的写「无相近题目」。
5. **运行环境**：做题与验收都在输入「本次运行」中给出的 WSL 发行版中进行。下面这些是出题时要满足的约束，不要写进 prompt（见「User Prompt 写法」）：
   - 命令行与服务端程序直接在 WSL 运行；
   - 网页类由 WSL 启动服务，在 Windows 浏览器访问 `localhost`；
   - 原生图形界面通过 WSLg 显示；
   - 依赖显卡能力（WebGPU、OpenGL 4.x、Vulkan、CUDA 等）时 `needs_gpu` 设为 true，并在 `gpu_note` 写明需要的能力与最低版本；
   - 禁止 docker，禁止要求 Windows 专属工具链（MSVC、DirectX、Windows API）。
6. **外部依赖**：题目依赖的外部网站或接口全部写进 `external_urls`（完整 https 地址）。避开需要登录、人机校验或明显反爬的站点；数据采集类题目优先选择公开、稳定、允许抓取的目标。
7. **素材**：0-1 题常常需要预置素材（测试视频、音轨、模型、贴图、样例数据、待分析的二进制等）。
   - 每个素材写一条 `materials`：放在仓库内的相对路径、用途、获取方式、许可说明、预计大小；
   - `source=url`：给可直接下载的 https 地址（`url`），`script` 写空字符串；
   - `source=script`：在仓库根目录执行即可生成的 bash 脚本（`script`，例如用 ffmpeg、python 合成测试数据），`url` 写空字符串；
   - `source=manual`：只能人工准备的素材，`url` 与 `script` 写空字符串，`purpose` 里写清楚要什么；
   - 单个文件不超过 100MB，尽量控制在 50MB 以内；优先公开许可素材（如 Blender 开放电影、Khronos glTF 样例）；
   - 没有素材时 `materials` 为空数组。
8. **环境需求**：`toolchain` 列出题目需要的系统级工具与最低版本（语言运行时、编译器、`ffmpeg` 这类命令行工具），`check_command` 是在 WSL 中能输出版本号的命令（如 `go version`、`ffmpeg -version`），`install_hint` 给 Ubuntu 下的安装命令。项目依赖（pip、npm、cargo 等包管理器装的库，如 numpy、express）不要写进 `toolchain`，做题时由模型在项目目录里自己安装。
9. **备注草稿**：`remark` 用一两句话写素材与环境前置条件，例如「0-1 开发。samples 预置 1080p 测试视频；需先安装 ffmpeg」。
10. **分支名**：`branch` 用小写字母、数字和连字符组成的项目短名（如 `live-relay`、`podcast-post`），不与已有题目重复。
11. **语言/框架**：`lang_framework` 只写语言与主要框架或库的名字，英文小写、不带版本号，用英文逗号分隔，不加空格和说明文字，例如 `java,python,nodejs`、`go,ffmpeg`、`typescript,webgpu`。

## User Prompt 写法

- 开头直接说要做什么，从这几种说法里选一种，同一批题目轮换着用，不要每题一样：「我在做一个……」「我想做个……」「帮我做一个……」。背景和为什么要做放在第二句，例如「我在做一个采访录音的对轨工具，几台录音机开机时间不一样，长录音还会慢慢错位……」。
- 不要写环境套话：「从空仓库做」「用 xx 在 Ubuntu-24.04 的 WSL 启动」「Windows 浏览器访问 localhost」「依赖就绪后断网可用」「不用 Docker」这类句子一律不写，做题环境由流水线保证，模型自己会处理。只有确实属于需求本身的约束才写，并且用这道题自己的话说，例如「现场没网，装好以后要能离线用」「只能用标准库，服务器上装不了第三方包」。
- 以真实用户口吻写，交代自己的背景和为什么要做这个东西，再说具体要求，像在给同事提需求。
- 正常使用中文标点，可以带少量代码片段或接口示例。
- 写清楚功能点与关键约束（性能、延迟、格式、兼容性、不能用某类现成库等），把难点自然地埋进需求里，不要直接告诉模型该怎么实现。
- 预置了素材时，在 prompt 里自然提一句素材放在哪里。
- 不使用「首先」「其次」「综上」「值得注意的是」等书面化表达，不用 markdown 标题。
- 语气平实克制，就是正常工作沟通的说法，不要刻意模仿口语：不用「烦死了」「很爽」「累死了」「绝了」「救命」「真香」「无语」「头大」之类情绪化或网络化的口头禅，也不要堆「啊」「呀」「哈哈」这类语气词；交代痛点时直接说事实（如「人工重跑已经漏过删除记录」），不靠情绪词渲染。
- 长度一般 150 到 500 字。

参考示例（风格参考，不得照抄题目）：

> 我想做个小型活动直播的推流服务，用 OBS 推流。SRS 那些现成的都试过，但还是想要个自己能完全掌控的轻量版，后面好往上加业务。用 Go 从头写：接 OBS 的 RTMP 推流，握手和 chunk 解析自己实现，别直接套现成的 RTMP 库。然后同时出两路：HTTP-FLV 给网页用 flv.js 播，延迟尽量压到 2 秒内；再出一路 HLS 给手机兜底。要支持多个房间同时直播，用推流地址里的 stream key 区分。观众中途进来要马上出画面，别黑屏等半天下一个关键帧。主播断流后重连，观众那边别直接挂掉。最后做个简单页面，输房间号就能看，页面上顺便显示下大概延迟多少。

## 内部验收要点

`acceptance_points` 每条是一个可验证的检查项，写清楚怎么验证、看到什么算通过，覆盖：每个明示功能点、埋进需求的隐性难点与边界条件、性能或格式类硬指标。这些要点不会出现在 prompt 中，只给验收环节使用。

## 输出

按 schema 输出 `{"tasks": [...]}`，题目数量等于输入中的数量。
