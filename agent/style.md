# Feedback 写作规范

适用于 Feedback、评分理由。后端会按本规范做规则检查（口吻、原分依据、代码锚点、质检会打回的表达），不通过的 Feedback 不能进入录屏环节。

## 核心标准

Feedback 不要求长，也不套固定模板，关键是读起来像懂行的人对这次任务的直接判断，并且过程、产物、证据、原分四件事能互相对上。只看这段文字，不知道题目名也能明白：模型具体做了什么，最终代码哪里有问题（或为什么确实完成），为什么会造成这个结果，问题在最终提交里是否还在，以及这些事实为什么对应这个分数。

四个标准缺一不可：

1. 有实际过程：模型在做题过程中做了什么 漏了什么 验证了什么 对用户宣称了什么，主要依据模型发给用户的消息和回复，工具调用和思考过程只用来核实，不写成分析轨迹得到的内容；1 到 4 分的过程问题以模型为主语单独成句，能脱离产物描述独立核验（见「过程问题怎么写」）。
2. 有最终产物：最终提交里还存在什么问题，或者为什么确实完成。
3. 有可定位证据：至少落到具体对象，文件 函数 代码行 测试结果 轨迹行为。
4. 原分说得通：结尾写明给几分，并且这个分数能由前面已核实的事实撑住。

## 篇幅与取舍

Feedback 不是问题清单，写透最关键的一两个点就够，质检看的是四件事能不能对上，不看写了多少条。

- 一般 150 到 300 字，不超过 400 字（后端超过 400 字会拦下）。
- 1 到 4 分：一个最关键的过程问题，加一到两个影响最大的产物问题；每个产物问题只给一个代码锚点（文件 函数 行号），不要一句话里堆好几个行号；其余问题不写进 Feedback。
- 5 分：写清改了哪个模块 怎么验证的 结果是什么，两三句话即可。
- 5 分写做好了什么；1 到 4 分只写没做好什么，做对的部分不写，最多在结尾给分时用半句说明核心能不能跑，作为分数依据。

## 视角与语气

- 不套固定开头：不要每篇都以「我让模型做某事」「我让它」开头，也不先复述题目需求；直接从最关键的事实写起，需求只在说明问题时顺带提到。开头可以是过程问题（模型改完只跑了某个测试），也可以是产物问题（某文件某函数怎么错了），按这一篇哪件事最关键来定。
- 主语按事实来：写模型的操作用「模型」，写自己实测看到的现象可以用「我」（如我导入截断的录音后仍显示分析完成），不强求第一人称。
- 平实直接，像给同事说清楚这次的结论，不写成评测报告，也不刻意吐槽或卖萌。
- 不用审稿模板：不写评审方 验收方 本轮任务 原始轨迹 验收结论这类质检口吻，不用固定分栏，不套「先总结完成项 再列两项缺陷 最后说核心可运行但未达标」的套路。
- 不使用 markdown：不要标题 列表符号 加粗 代码块 表格。

## 标点与格式（硬性）

- 中文标点只用四种简单的：逗号，句号。顿号、分号；用来断句和分隔并列项。其余中文标点一律不用（：？！“”（）《》【】…— 等都不行），句子短时也可以继续用空格断句。
- 英文全部小写，包括文件名、函数名、报错、命令、产品名，例如 `date.py` `valueerror` `readme.md` `ffmpeg` `webgpu`。
- 文件名、路径、版本号、命令、数值中英文词内部的 `.` `/` `-` `_` `:` 可以保留，例如 `src/utils/date.py` `src/parser.py:82` `v22.23.2` `-16lufs` `localhost:20001`；但不能出现在词尾当句号或冒号用。
- 逗号、分号、括号、引号、问号、感叹号等英文标点一律不用（断句用上面的中文，。、；）；函数名不带括号，写 `parse_response` 不写 `parse_response()`。
- 不用反引号包代码、文件名和命令。本文档里的反引号只是为了标出示例，Feedback 原文里一个反引号都不能有。
- 函数名、变量名、报错里的驼峰和大写也全部改成小写，如 renderEventEditor 写成 rendereventeditor，ALL E2E PASSED 写成all e2e passed。
- 命令只写主体，如 node tests/e2e.js、npm test，不写重定向、管道、&&、$() 和环境变量前缀，`2>&1 | tail -3`、`>/dev/null`、`NODE_PATH=$(npm root -g)` 这类都去掉；几条命令之间用和连接。
- 报错原文去掉括号和引号，如 `Cannot read properties of undefined (reading 'length')` 写成cannot read properties of undefined reading length；表达式不照抄代码，如 `math.min(...img.values)` 写成把img.values展开传给math.min。
- 行号范围用至，如第763至764行；并列项用顿号，不用斜杠，如绘制、擦除；不写独立的斜杠和省略号，如 33 / all passed 写成33项全过。
- 中文与英文、中文与数字之间不加空格，例如「运行npm run dev后页面白屏」「延迟大概3秒」。
- 空格只用来断句：断句处的空格可以紧挨英文或数字（如「页面报typeerror 刷新也没用」）；但不要在英文或数字两边都加空格（「我点了 play 按钮」不行，应写「我点了play按钮」）。标点前后不加空格，如「返回5 passed，就宣称完成。」。

## 推荐写法

用一段自然的话写完，下面是要覆盖的内容，不是固定句式，顺序也可以调换：

【具体操作】 用【具体测试或轨迹行为】验证了【范围】 最终产物里【文件 函数 代码行】【具体缺陷 或完成情况】 会造成【用户或业务影响】 这个问题在最终提交里【仍然存在 或已经修好】 所以给【X】分

不需要写问题 证据 影响这类小标题，也不用固定引导词。1 到 4 分时过程和产物各自成句、用句号分开，让边界一眼可见：过程那句以模型起句，写模型在过程中做了什么或漏了什么；产物那句落到最终提交的文件和代码。先写哪部分、怎么衔接按这一篇的内容来，不要篇篇都是同一个句式，例如不要每篇都写成「过程上，轨迹第N行……。产物上，最终提交的……」（后端会拦下同时出现过程上和产物上的写法）。

### 5 分

只写做好了什么：写清楚改了哪个模块 怎么验证的 最终实现了哪些需求 测试结果与最终提交是否一致 为什么撑得起满分。不要为了凑格式硬编缺点，但也不能只写「功能完整 测试全过 表现优秀 给5分」这种没有具体对象的话。

### 1 到 4 分

只写没做好什么，做对的部分不写。必须同时写出过程问题和产物问题，每个产物问题都要有：

- 代码锚点：文件 函数 尽量带行号，如 `src/parser.py:82` 的 `parse_response`；
- 代码原因：哪段逻辑怎么错了，如没判断空响应就直接调用 `response.json`；
- 业务影响：用户会遇到什么，如批量导入在这条记录处整体中止；
- 最终状态：问题在最终提交里仍然存在。

界面报错 交互异常 功能缺失本身只算产物现象，必须追到代码原因；只说测试没做全而不说最终代码哪里错，也不够。

### 过程问题怎么写

1 到 4 分的过程问题是质检单独核对的一项，过程和产物分开写成各自成立的两句（先后不限），不能只在产物缺陷前面挂一句「模型的某测试只验了某项」，也不要从行号一路连写到给分。

过程问题写的是模型在做题过程中的问题，读起来要像看着模型干活的人说的话，不像分析轨迹文件得出的结论：

- 主语是模型，直接写它漏做或错做了什么验证，如模型没有通过页面的文件选择入口验证波形是否更新，也没有在同一页换入第二对有效wav，或核对手动导入后检查点续算按钮的状态；不要写成测试脚本覆盖了什么，如脚本只断言了某项、用例只检查了某项，质检会认为没写出模型自身漏做的环节；
- 依据模型的消息和回复：模型对用户说了什么，宣称哪些已经验证、哪些已经通过，交付时怎么总结的，再对照它实际没做的那一步，如模型只跑了单元测试就回复说端到端全部通过 但从没在页面上点过导出确认能下载；模型改松测试容差 删改断言 承认了偏差却没处理时要写出来，这是最有力的过程证据；
- 不复述工具调用和思考过程：不写轨迹第几行运行什么 第几行返回什么 这种逐行串起来的命令和输出，也不引用模型思考里的内容；
- 可以带一个行号帮质检定位，放在动作后面顺带一提，如模型在第1729行只通过测试接口导入了一对文件就判定导入正常；不以行号起句，不写轨迹二字，全篇最多一两个行号；
- 说清关系：这个漏验怎样让后面写的产物缺陷带进了交付，如这几项漏验让下面两处缺陷带进了交付；这一句不能省，它是过程那句的收尾。

写进去的动作和宣称都要在完整轨迹里核对过，定位不到的不写，不编行号。过程问题要和后面写的产物问题对应同一件事，不要写一个与产物缺陷无关的过程问题。

模型的判断 想法 误诊本身不是过程问题，例如模型判断成缺中文字体就没再处理 模型以为浏览器会自动处理编码。质检只能核对动作，要写就落到模型回复里下的结论和之后缺的那一步检查，如模型回复说中文显示正常 但它没有打开页面截图看过；定位不到具体回复和动作的判断不写，换成能定位的验证动作。

## 一定会被打回的写法

- 只有产物现象没有过程问题，例如只有页面抖动 接口报错 功能缺失。
- 只有过程问题没有最终产物问题，例如只说测试没做全。
- 过程问题混写在产物缺陷清单里，或只写模型的某测试只验了某项 没核对某项，没写模型具体漏做了哪个验证以及它和最终缺陷的关系，质检无法独立核验。
- 过程问题的主语不是模型，只写测试脚本覆盖了什么 漏查了什么，例如脚本通过接口验证了内部状态 漏查页面刷新，质检认为没写出模型自身漏做或错做的环节。
- 过程写成轨迹分析，例如轨迹第199行运行某命令 第200行返回all pass 两段脚本核对了固定样例，读起来是分析轨迹得到的内容，不是模型在过程中的问题。
- 过程与产物连成一段没有边界，例如从行号一路写到给几分，分不清哪句是过程哪句是产物。
- 篇篇套同一个模板，例如都写成过程上……。产物上……。
- 把模型的判断或误诊当过程问题，例如模型判断成缺字体就没再处理，没有对应的命令 截图 回复所在的轨迹位置。
- 只有文件名没有代码原因，例如只说 `parser.py` 有问题。
- 代码原因只写在证据清单或评分理由里，Feedback 原文没写。
- 用见原文 见文件与行号 同上 见上文之类的占位指代。
- 写测试通过 但实际没有执行对应断言；数量说过头，例如跑了200轮就说做了200次逐行比较。
- 中间失败后来修好了 却写成最终产物失败；要写清是中间版本的问题还是最终提交的问题。
- 把网络 api 代理 网关 平台超时或工具重跑写成模型的过程问题。
- 把工具链或shell环境的噪声写成模型的过程问题，例如git bash对路径或url的自动转换 msys路径改写；模型对这类现象的判断不能用来评价它的方案。
- 整体表现不错但仍有提升空间 建议修复 还需修复 之类可以套到任何任务上的空话。
- 每篇都用同一个开头，例如都以我让模型做某事开头 先复述一遍需求再说问题。
- 把发现的问题全部罗列出来 写成好几百字的问题清单。
- 把题面和包内约定都没要求的行为写成缺陷，例如要求导出的配置能重新导入 要求导入非法文件后保留上一份规则或结果；对非法输入只有出现崩溃 nan 白屏 页面显示与内部状态不一致 报错没指出是哪一项这类实际错误时才算问题。
- 把实现形态当缺陷，例如题面没要求异步却扣分说在主线程同步求解、没有取消入口，题面没要求导入本地文件却扣分说只能用内置预设，题面要求能调阈值、已有阈值输入却扣分说图例不能点击显隐；只有题面写明了某种形态或交互方式，才能按它扣分。

首先 其次 再次 综上 综上所述 总而言之 总的来说 值得注意的是 需要注意的是 需要指出的是 不难发现 显而易见 毋庸置疑 至关重要 赋能 一方面 另一方面 此外 与此同时 由此可见 整体而言 总体而言 具体而言 综合来看

## 示例

5 分：
模型在src/sync.py里补了按游标续拉的增量同步分支，改完跑了pytest tests/test_sync.py，3个用例都过了。我又在最终提交上重跑一遍，结果一致。首次同步、断点续传、重复记录去重这三条需求都能对上，没发现遗留失败，交付是完整的，给5分。

3 分：
模型改完parser只跑了正常响应的用例，看到5 passed就回复说解析和错误处理都验证过了，tests/test_error_handling.py它一次都没运行，空输入和超时两条路径从头到尾没人试过，这个漏验让下面的错误带进了交付。最终提交里src/parser.py:82的parse_response遇到空响应直接调用response.json，没先看状态码和内容是否为空，会抛jsondecodeerror，批量导入在这条记录处整体中止，这个问题在最终提交里还在。主流程能跑但错误路径没兜住，给3分。

2 分：
prompt要求断流重连后观众端不断开，我在obs里停推再开，flv.js页面直接报mediaerror卡死。server/relay.go的onpublishend在断流时直接close了所有订阅者的conn，没有保留订阅等待重连，最终提交里还是这样。模型写完relay.go只跑了go build，没有一次推流再断流的实测，就在回复里说断流续播已经完成，核心功能因此坏着交付了。断流续播没实现，给2分。

4 分：
模型交付前没有在页面上用正常操作试过最大尺寸的输入，它在第1406行收尾只重跑了单元测试和小样例的浏览器测试，就回复说输入校验和大图导入都已覆盖，这处漏验让大图问题留在了交付里。app/ui.js:95把1048576个节点值整体展开传给math.min，我导入1024乘1024的16位灰度图时页面报maximum call stack size exceeded，提取按钮一直是灰的，最终提交里还在。其余需求都能对上，只有最大尺寸这一项没达成，给4分。
